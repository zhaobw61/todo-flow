# W2 需求规格

## 目标

把用户的一句话功能需求，整理成明确的需求、验收标准、技术设计和任务清单。

## 输入

- 用户提出的功能需求；
- W1 生成的项目状态摘要；
- 项目已有代码和文档。

## 执行步骤

1. 读取用户需求、W1 项目状态摘要和相关代码；
2. 用一句话重新描述用户想解决的问题；
3. 明确本次功能包含什么、不包含什么；
4. 将需求转换成可以实际验证的验收标准；
5. 根据现有项目结构编写技术设计；
6. 将设计拆分成小而明确的开发任务；
7. 标记任务之间的依赖关系和执行顺序；
8. 生成需求、设计和任务文档。

## 输出

在 `specs/<feature-name>/` 目录中生成以下文件：

### requirements.md

记录：

- 功能背景和目标；
- 本次包含的范围；
- 本次不包含的范围；
- 可以实际验证的验收标准；
- 需要用户确认的问题。

### design.md

记录：

- 当前项目相关代码；
- 准备修改的文件；
- 数据结构和状态变化；
- 实现方案；
- 可能的风险；
- 测试方案。

### tasks.md

将技术设计拆分成任务清单：

- [ ] 任务一
- [ ] 任务二
- [ ] 任务三

每个任务需要说明：

- 要完成什么；
- 依赖哪些任务；
- 预计修改哪些文件；
- 怎样验证完成。

同时更新 `specs/INDEX.md`，登记当前 Feature 及其状态。


## 可调用能力

### 需求分析 Skill

调用需求分析 Skill，帮助完成：

- 澄清用户真正想解决的问题；
- 区分功能范围和非功能范围；
- 将模糊需求转换成可验证的验收标准；
- 检查需求、设计和任务是否互相对应。

### 代码探索 SubAgent

只有在功能涉及多个模块、主 Agent 难以快速确定影响范围时，才调用只读代码探索 SubAgent。

SubAgent 负责：

- 查找与当前功能相关的文件；
- 分析现有数据流和组件关系；
- 汇总可能受影响的模块；
- 返回分析结果，不修改代码。

如果主 Agent 通过直接读取少量文件就能了解项目，则不创建 SubAgent。

## 完成条件

只有同时满足以下条件，W2 才算完成：

- 功能目标已经明确；
- 功能范围和非功能范围已经写清楚；
- 每一条验收标准都可以通过测试或实际操作验证；
- 技术设计与当前项目结构相符；
- 每个任务都足够小，并且有明确的验证方式；
- 任务之间的依赖关系已经标记；
- `requirements.md`、`design.md` 和 `tasks.md` 已经生成；
- `specs/INDEX.md` 已经更新；
- 不存在会阻止开发的关键未确认问题。

完成后进入 W3，由 W3 读取任务清单并领取第一个未完成任务。

## 停止条件

出现以下任意情况时，暂停工作流并向用户提问：

- 用户需求存在多种会明显影响实现方式的解释；
- 无法确定功能范围或验收标准；
- 用户要求与项目现有规则冲突；
- 功能需要用户选择第三方服务、账号、付费方案或数据存储方式；
- 功能可能删除、覆盖或迁移现有数据；
- 无法在不修改无关模块的情况下完成设计。

停止时需要说明：

- 当前已经确认了什么；
- 还有什么没有确认；
- 为什么这个问题会影响后续开发；
- 用户需要做出什么决定。
