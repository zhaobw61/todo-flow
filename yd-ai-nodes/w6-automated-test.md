# W6 自动化测试

## 目标

根据当前 Feature 的验收标准，启动项目并通过浏览器自动化工具执行真实操作测试。

本节点优先使用 Playwright MCP 操作页面、观察结果并记录证据。测试失败时由 Claude 在当前任务范围内修复，然后重新执行 W6，不再返回 W5 重复进行 Codex 审查。

## 输入

- 当前 Feature 的 `requirements.md` 和验收标准；
- 当前 Feature 的 `design.md`；
- W3 生成的 `current-batch.md`；
- W4 生成的 `development-report.md`；
- W5 生成的 `code-review-report.md`；
- 项目的启动和测试命令；
- 当前工作区代码。

## 执行步骤

1. 读取验收标准，把每条标准转换成可执行的测试场景；
2. 从项目配置中确认正确的安装、启动和测试命令；
3. 启动本地项目并确认测试地址可以访问；
4. 运行项目已有的静态检查和自动化测试；
5. 使用 Playwright MCP 打开页面并执行真实用户操作；
6. 检查页面结果、浏览器控制台错误和移动端布局；
7. 记录每个测试场景的预期结果、实际结果和证据；
8. 如果测试失败，判断是代码问题、规格问题还是环境问题；
9. 代码问题由 Claude 在当前任务范围内修复，然后重新执行 W6；
10. 所有验收场景通过后，生成测试报告并进入 W7。

## 测试循环

### 代码问题

如果失败由本批代码引起：

1. 记录失败场景和错误证据；
2. Claude 进行最小范围修复；
3. 重新运行失败场景；
4. 重新运行受影响的相关场景；
5. 更新测试结果。

修复后直接重跑 W6，不再返回 W5。

### 规格问题

如果验收标准不明确或互相矛盾，停止测试并返回 W2 补充规格。

### 基线既有问题

如果静态检查或自动化测试失败，不得立刻认定为本 Feature 的问题，也不得直接忽略。

必须：

1. 记录失败命令、错误位置和错误内容；
2. 检查失败涉及的文件是否被本 Feature 修改；
3. 使用 Git 基线确认该失败在本 Feature 开始前是否已经存在；
4. 只有确认“修改前已失败”且“与本 Feature 无关”时，才能标记为既有问题；
5. 在 `test-report.md` 中记录验证证据和未修复原因；
6. 确认本 Feature 没有新增失败或使既有失败恶化。

无法通过 Git 基线确认时，暂停并询问用户，不得自行把失败标记为既有问题。

### 环境问题

如果项目无法启动、浏览器工具不可用或外部服务异常，停止测试并报告环境问题，不得把环境失败记录为代码失败。

## 输出

在当前 Feature 目录生成 `test-report.md`，至少记录：

- 测试环境和页面地址；
- 实际执行的启动、检查和测试命令；
- 每个验收标准对应的测试场景；
- 每个场景的操作步骤；
- 预期结果和实际结果；
- 通过或失败状态；
- 截图、控制台信息等测试证据；
- 测试中发现的问题及修复记录；
- 移动端和浏览器控制台检查结果；
- 经 Git 基线验证的既有失败及证据；
- 最终是否允许进入 W7。

## 路由与完成条件

满足以下条件时进入 W7：

- 所有本批验收场景均已执行并通过；
- 静态检查和自动化测试已经通过，或者其中的失败已通过 Git 基线验证为与本 Feature 无关的既有问题；
- 本 Feature 没有新增失败，也没有使既有失败恶化；
- 浏览器控制台没有阻断性错误；
- 移动端布局没有出现阻断性问题；
- 测试失败后的修复已经重新验证；
- 已生成完整的 `test-report.md`；
- 没有把未执行的测试写成通过。

## 停止条件

出现以下情况时暂停并报告：

- 项目无法启动；
- Playwright MCP 或测试环境不可用；
- 验收标准无法转换成可执行测试；
- 测试持续失败且无法在当前任务范围内修复；
- 修复需要扩大 Feature 范围；
- 测试可能修改或删除真实用户数据；
- 需要账号、密钥或外部权限才能继续。

停止时记录失败证据、已尝试的方法以及需要用户处理的内容。
